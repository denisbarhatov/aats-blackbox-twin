# BlackBox Twin — תוכנית POC

**המטרה:** להוכיח שהמערכת לומדת לבד את מכונת המצבים של בקר ESP32, בלי לראות את הקוד שלו, ובונה תאום שמתנהג כמוהו גם על רצפי פקודות שלא שימשו בלמידה. כל זה רץ ב-AWS, והבקר מחובר דרך AWS IoT Core.

> סטטוס: תוכנית. עוד לא נכתב קוד.
> מסגרת: פרויקט גמר בקורס AWS.

---

## 1. היקף

**בתוך ה-POC:**
- מכשיר אחד: ESP32 עם נורת LED, ובנוסף סימולטור ב-Python שמתנהג בדיוק כמוהו.
- פרוטוקול אחד: הודעות JSON מעל MQTT, דרך AWS IoT Core.
- 5 פקודות ו-4 מצבים (פירוט בסעיף 2).
- למידה אקטיבית: המערכת שולחת ניסויים בעצמה ולא רק מקשיבה.
- תאום שרץ בענן, דוח התאמה ודאשבורד בסיסי.

**מחוץ ל-POC:**
- מכשירים או פרוטוקולים נוספים.
- למידה פסיבית מהקלטות PCAP. זה שלב מאוחר יותר.
- ניהול משתמשים, הרשאות מתקדמות וחיוב.
- AI או LLM.

## 2. המכשיר: מכונת המצבים "הנסתרת"

ה-Firmware מממש את מכונת המצבים שבטבלה. מנוע הלמידה **לא** רואה את הטבלה הזאת. היא משמשת אותנו רק לבדיקה אם הלמידה הצליחה.

**פקודות:** `ON`, `OFF`, `STATUS`, `RESET`, `PING`

| מצב | `ON` | `OFF` | `STATUS` | `RESET` | `PING` |
|---|---|---|---|---|---|
| `OFF` | `OK` → `ON` | `OK` → `OFF` | `LED_OFF` | `RESET_OK` → `OFF` | `PONG` |
| `ON` | `WARN` → `WARN` | `OK` → `OFF` | `LED_ON` | `RESET_OK` → `OFF` | `PONG` |
| `WARN` | `ERR` → `FAULT` | `OK` → `OFF` | `LED_ON` | `RESET_OK` → `OFF` | `PONG` |
| `FAULT` | `ERR` | `ERR` | `FAULT` | `RESET_OK` → `OFF` | `ERR` |

**למה ככה:**
- `ON` מחזיר תשובה שונה לפי מה שקרה קודם, ולכן אי אפשר לחקות את המכשיר עם טבלה פשוטה של בקשה ותשובה.
- `FAULT` הוא מצב "תקוע" שרק `RESET` משחרר. זה מצב שקשה לגלות בלי ניסויים אקטיביים.
- `RESET` מחזיר תמיד למצב התחלתי ידוע. L\* חייב את זה כדי שכל ניסוי יתחיל מאותה נקודה.

## 3. ארכיטקטורה

```text
            ┌──────────────────────── AWS ─────────────────────────┐
            │                                                      │
 ESP32 ◄────MQTT/TLS────► IoT Core ◄────► Learner  (ECS Fargate)   │
 (Thing)    │               │   ▲                                  │
            │               │   └───────► Twin     (ECS Fargate)   │
 Simulator ◄┘               │   ▲                                  │
 (Thing)    │               │   └───────► Validator (ECS Fargate)  │
            │               ▼                                      │
            │   IoT Rule → S3  (raw log of every message)          │
            │                                                      │
            │   Dashboard (S3 + CloudFront)                        │
            │      → API Gateway + Lambda → Step Functions         │
            │   S3: model.json, results   ·   CloudWatch: logs     │
            └──────────────────────────────────────────────────────┘
```

### רכיבים

| רכיב | טכנולוגיה | מה הוא עושה |
|---|---|---|
| ESP32 Firmware | Arduino / ESP-IDF + MQTT over TLS | מממש את מכונת המצבים ועונה לפקודות |
| Simulator | Python + AWS IoT Device SDK | אותו פרוטוקול ואותה התנהגות כמו הבקר. מאפשר לפתח בלי חומרה |
| Learner | Python + AALpy (אלגוריתם L\*) | שולח ניסויים, מסיק מכונת מצבים, שומר `model.json` |
| Twin Runtime | Python | טוען `model.json` ועונה על פקודות לפיו |
| Validator | Python | שולח אותם רצפים למקור ולתאום, משווה, ומחשב אחוז התאמה |
| Baseline | Python | חיקוי "הקלט והשמע" פשוט, להשוואה |
| Orchestration | Step Functions + Lambda | מריץ את השלבים לפי הסדר |
| Dashboard | אתר סטטי ב-S3 + CloudFront | כפתור "התחל", גרף מצבים, אחוזים, כשלונות |

## 4. AWS IoT Core: איך החיבור עובד

### Things
- `bbt-esp32-01`: הבקר הפיזי.
- `bbt-sim-01`: הסימולטור.
- `bbt-twin-01`: התאום.

### Topics

| Topic | כיוון | תוכן |
|---|---|---|
| `bbt/<device-id>/cmd` | ענן → מכשיר | `{"id": 17, "cmd": "ON"}` |
| `bbt/<device-id>/resp` | מכשיר → ענן | `{"id": 17, "out": "OK"}` |
| `bbt/<device-id>/status` | מכשיר → ענן | `online` / `offline` (דרך Last Will) |

### כללים
- **`id` בכל הודעה.** MQTT לא מחכה לתשובה, וה-`id` מחבר כל תשובה לפקודה שלה.
- **Timeout של 2 שניות.** אם אין תשובה בזמן, הלומד רושם `TIMEOUT` ומתייחס לזה כאל תשובה.
- **QoS 1** לפקודות ולתשובות.
- **התאום מדבר באותו פרוטוקול.** אותו קוד בדיקה עובד מול הבקר, מול הסימולטור ומול התאום, ומחליפים רק את ה-`device-id`.

### אבטחה
- תעודת X.509 נפרדת לכל Thing. IoT Policy לכל Thing מרשה לו רק את ה-Topics שלו.
- ה-Tasks ב-Fargate (Learner, Twin, Validator) מתחברים דרך WebSocket עם הרשאות IAM של ה-Task Role. כך אין תעודות בתוך ה-Container.
- הלומד שולח רק פקודות מתוך Allowlist, עם הגבלת קצב.
- הבקר לא חשוף לאינטרנט: הוא רק פותח חיבור יוצא ל-IoT Core.

### ⚠️ לא להשתמש ב-Device Shadow לדיווח המצב
אם הבקר מדווח "אני ב-WARN", הלמידה מאבדת את המשמעות שלה. כל הטענה של הפרויקט היא שהמצבים מתגלים **רק מתוך התשובות**. ה-Shadow מתאים לכל היותר למידע כמו גרסת Firmware.

## 5. זרימת העבודה (Step Functions)

```text
Start (from Dashboard)
  ↓
1. Check device is online           (Lambda)
  ↓
2. Learn                             (Fargate: Learner)
   → model.json → S3
  ↓
3. Deploy twin                       (Fargate: Twin, loads model.json)
  ↓
4. Validate                          (Fargate: Validator)
   - N new random sequences → device + twin + baseline
   → results.json → S3
  ↓
5. Done → Dashboard shows the state graph + match rates
```

## 6. איך יודעים שה-POC הצליח

| מדד | יעד ראשוני* |
|---|---|
| מצבים שהתגלו | 4 מתוך 4, עם המעברים הנכונים |
| התאמת התאום על רצפים חדשים | 95% ומעלה |
| התאמת Baseline (הקלט והשמע) | נמוך משמעותית מהתאום |
| זמן מלחיצה על "התחל" ועד תאום רץ | עד 15 דקות |

\* היעדים הם הערכה. נקבע אותם סופית אחרי ההרצה הראשונה מול הסימולטור.

**ההדגמה:**
1. מראים את הבקר עובד: מדליקים ומכבים את הנורה.
2. לוחצים "התחל למידה" ורואים את הניסויים זורמים בזמן אמת.
3. גרף המצבים מופיע, כולל `WARN` ו-`FAULT` שהמערכת גילתה לבד.
4. מנתקים את הבקר ומפנים את הלקוח לתאום. הלקוח ממשיך לעבוד.
5. מציגים את אחוזי ההתאמה: תאום מול Baseline.

## 8. סיכונים

| סיכון | מה עושים |
|---|---|
| ה-ESP32 מתנתק באמצע למידה | Last Will מסמן ניתוק, והלומד עוצר ומחכה. אפשר להמשיך מאותה נקודה |

| L\* מחליט שהמודל "נכון" מוקדם מדי | בדיקות Equivalence עם הרבה רצפים אקראיים, ובדיקה נפרדת מול הסימולטור |
| עלויות AWS | Fargate רץ רק בזמן עבודה. להגדיר Budget Alert |
