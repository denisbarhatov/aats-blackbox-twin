# BlackBox Twin — הסבר פשוט

**בשורה אחת:** BlackBox Twin מקשיב לתקשורת של מכשיר, לומד ממנה איך המכשיר מתנהג, ובונה ממנו "תאום" וירטואלי שאפשר לבדוק מולו תוכנה. לא צריך בשביל זה את קוד המקור של המכשיר, וגם לא את המכשיר הפיזי.

> סטטוס: רעיון בשלב תכנון. עוד לא נכתב קוד.

---

## 1. מה זה?

תחשוב על **חיקוי קול**. מישהו שומע אותך מדבר הרבה, לומד איך אתה עונה על שאלות, ואחר כך יכול "להיות אתה" בטלפון.

BlackBox Twin עושה את אותו הדבר, אבל למכשירים:

- **"מכשיר"**: בקר במפעל, שרת ישן, ציוד רשת, מכשיר IoT. כל דבר שמדבר עם תוכנה דרך הרשת.
- **"קופסה שחורה"**: אין לנו את הקוד שלו ואין תיעוד מלא. רואים רק מה נכנס ומה יוצא.
- **"תאום"**: תוכנה שמתנהגת כמו המכשיר, ואפשר להריץ אותה על כל מחשב.

### דוגמה מהמפעל

במפעל יש מכונה עם בקר. תוכנת הניהול שולחת לו פקודות כמו "התחל", "עצור" ו"מה המצב?". המפתחים רוצים לשדרג את התוכנה, אבל:

- הבקר נמצא בייצור, ואסור לגעת בו.
- יש רק בקר אחד, והוא יקר.
- אי אפשר לגרום לו "להתקלקל" בכוונה כדי לבדוק איך התוכנה מגיבה.

**עם BlackBox Twin:** מקליטים את השיחות בין התוכנה לבקר, המערכת בונה תאום, והמפתחים עובדים מול התאום. בתאום אפשר גם לגרום לתקלות בכוונה, וזה לא מזיק לאף אחד.

---

## 2. איך משתמשים? (מנקודת המבט של המשתמש)

1. **מקליטים.** מחברים "מאזין" לרשת בסביבת בדיקות מורשית, ומקליטים את השיחות בין התוכנה למכשיר. התוצאה היא קובץ הקלטה (PCAP).
2. **מעלים.** מעלים את הקובץ ל-BlackBox Twin.
3. **מחכים ללמידה.** המערכת מנתחת את ההקלטה ומציגה מה הבינה: אילו פקודות יש, אילו תשובות, ובאילו "מצבים" המכשיר יכול להיות.
4. **(אופציונלי) מאשרים ניסויים.** המערכת מציעה: "אני לא בטוחה מה קורה אם שולחים עצור פעמיים. מותר לי לבדוק?". אם מאשרים, היא שולחת את הפקודה למכשיר **במעבדה בלבד** ולומדת מהתשובה.
5. **מקבלים תאום.** המערכת מייצרת תאום שרץ ב-Docker, כלומר תוכנה ארוזה שרצה על כל מחשב או שרת.
6. **מחברים את התוכנה לתאום.** משנים בתוכנה את הכתובת של המכשיר לכתובת של התאום. התוכנה לא יודעת שהיא מדברת עם חיקוי.
7. **מקבלים דוח אמינות.** למשל: "התאום מתנהג כמו המקור ב-92% מהבדיקות. אלה המקרים שבהם הוא שונה, ואלה הדברים שעוד לא נבדקו".
8. **מדמים תקלות.** לוחצים "תחזיר שגיאה" או "תתנתק אחרי 5 שניות" ובודקים שהתוכנה מתמודדת.

## 3. איך זה עובד מבפנים?

המערכת **לא כותבת קוד חדש** לכל מכשיר. היא בונה **"מפה" של ההתנהגות** (קובץ נתונים), ויש **מנוע אחד כללי** שקורא את המפה ומתנהג לפיה.

> כמו נגן מוזיקה: הנגן הוא אותה תוכנה תמיד, והשיר (המפה) משתנה.

### 4 שלבי הלמידה

**שלב 1: פירוק לשיחות.**
ההקלטה היא ערימה של חבילות מידע. המערכת מסדרת אותן לזוגות של "שאלה ותשובה":

```text
תוכנה ← → מכשיר
LOGIN admin       →  OK SESSION=7f3a
START motor=2     →  OK STATE=RUNNING
START motor=2     →  ERR ALREADY_RUNNING
STOP              →  OK STATE=IDLE
```

**שלב 2: הבנת מבנה ההודעה.**
המערכת משווה הרבה הודעות ומזהה איזה חלק קבוע ואיזה משתנה:
- `START` תמיד קבוע, אז זה **שם הפקודה**.
- `motor=2` משתנה, אז זה **פרמטר**.
- `SESSION=7f3a` הוא **מזהה**: המכשיר נותן אותו, והוא חוזר בהודעות הבאות.

**שלב 3: לימוד המצבים (החלק החשוב).**
אותה פקודה `START` קיבלה פעם `OK` ופעם `ERR`. מזה המערכת מבינה שלמכשיר יש **זיכרון**, כלומר "מצבים":

```text
        START → OK
[מנוחה] ─────────────→ [פועל]
   ↑                     │  START → ERR (כבר פועל)
   └──── STOP → OK ──────┘
```

את זה עושים עם אלגוריתמים מוכרים מהמחקר ללמידת "מכונות מצבים", כמו L\*. יש להם ספריות מוכנות ב-Python (AALpy).

**שלב 4: כללים לתשובות.**
המערכת לא מחזירה תשובה מוקלטת אחת לאחת. היא לומדת **כללים**, למשל "להחזיר את מספר ה-SESSION שהלקוח שלח" או "לייצר מזהה חדש בכל התחברות".

### ואז: בדיקה מול המקור
שולחים **את אותם רצפים** גם למכשיר האמיתי וגם לתאום, ומשווים את התשובות. ככה יודעים, במספרים, כמה התאום נאמן.

## 4. תמונת הארכיטקטורה

```text
 ┌─────────────── 1. למידה ───────────────┐
 │                                        │
 │  הקלטה (PCAP)                          │
 │      ↓                                 │
 │  פירוק לשיחות  (Session Parser)        │
 │      ↓                                 │
 │  זיהוי מבנה הודעות (Format Inference)  │
 │      ↓                                 │
 │  לימוד מצבים (State Learner) ⇄ ניסויים במעבדה │
 │      ↓                                 │
 │  "מפת התנהגות"  (twin_model.json)      │
 └────────────────────────────────────────┘
                   ↓
 ┌─────────────── 2. הרצה ────────────────┐
 │  Twin Runtime — שרת שקורא את המפה      │
 │  רץ ב-Docker, + הזרקת תקלות            │
 └────────────────────────────────────────┘
                   ↓
 ┌─────────────── 3. אימות ───────────────┐
 │  בודק השוואה: מקור מול תאום            │
 │      ↓                                 │
 │  Dashboard: מצבים, אחוז התאמה, פערים   │
 └────────────────────────────────────────┘
```

| חלק | מה הוא עושה, במילים פשוטות |
|---|---|
| Session Parser | מסדר את ההקלטה לשיחות של שאלה ותשובה |
| Format Inference | מבין ממה בנויה כל הודעה |
| State Learner | מגלה באילו מצבים המכשיר יכול להיות ומה מעביר ביניהם |
| Active Probe Planner | מחליט איזה ניסוי כדאי לעשות כדי ללמוד עוד (רק באישור) |
| Twin Runtime | ה"שחקן" שמשחק את המכשיר לפי המפה |
| Differential Tester | בודק שהתאום עונה כמו המקור |
| Dashboard | המסך שבו המשתמש רואה הכל |

## 5. איפה AWS נכנס?

**חשוב לדעת:** AWS **לא חובה**. את ה-MVP (הגרסה הראשונה) אפשר להריץ כולו על מחשב אחד עם Docker. AWS נכנס כשרוצים שזה יעבוד כשירות בענן: כמה משתמשים, הרבה הקלטות, ותאומים שרצים כל הזמן.

| חלק במערכת | שירות AWS | למה |
|---|---|---|
| שמירת הקלטות PCAP | **S3** | אחסון קבצים זול ובטוח |
| הרצת הלמידה (עבודה כבדה, מדי פעם) | **AWS Batch** או **ECS Fargate** | מפעילים מחשב רק כשצריך ומשלמים רק על זמן ריצה |
| ניהול שלבי הלמידה ברצף | **Step Functions** | מריץ את השלבים לפי הסדר: פירוק, מבנה, מצבים, תאום |
| הרצת התאומים | **ECS Fargate** + **ECR** | כל תאום הוא Container. ECR שומר את האריזות |
| Backend (FastAPI) | **ECS Fargate** או **App Runner** | השרת שהממשק מדבר איתו |
| בסיס נתונים | **RDS PostgreSQL** | שומר פרויקטים, מודלים ותוצאות בדיקה |
| ממשק (Dashboard) | **Amplify** או **S3 + CloudFront** | אתר מהיר וזמין |
| AI (אופציונלי) | **Bedrock** | לתת שמות הגיוניים לשדות ולהסביר פערים במילים |
| ניטור ולוגים | **CloudWatch** | לראות מה רץ ומה נכשל |
| הרשאות ומשתמשים | **IAM** + **Cognito** | מי רשאי לראות ולהעלות מה |

**המלצה:** לבנות קודם הכל מקומית עם Docker, ורק כשה-MVP עובד להעביר ל-AWS. אם יש דרישה מהמסגרת (קורס או תחרות) להשתמש ב-AWS, השלב הכי טבעי להתחיל ממנו הוא **S3 להקלטות + Fargate לתאומים**.

## 6. מתחרים

**כן, יש מתחרים.** רובם עושים חלק מהעבודה, אבל לא את כולה.

| כלי | מה הוא עושה | מה חסר לו לעומתנו |
|---|---|---|
| **Parasoft Virtualize** | כלי מסחרי גדול לחיקוי שירותים | בעיקר הקלטה וכללים שאדם כותב. לא לומד מצבים לבד |
| **Broadcom Service Virtualization** (לשעבר CA DevTest) | כלי Enterprise ותיק לחיקוי שירותים | יקר ומורכב, ומבוסס בעיקר על הקלטה |
| **Traffic Parrot** | חיקוי שירותים לבדיקות | לא מודד כמה החיקוי נאמן למקור |
| **WireMock / Mountebank / Hoverfly** | קוד פתוח, Mock לשירותים (בעיקר HTTP) | האדם כותב את ההתנהגות בעצמו |
| **Keploy / Speedscale** | מקליטים תעבורת API ומשדרים אותה מחדש | בעיקר "הקלט והשמע", לא למידת התנהגות |
| **Netzob** | קוד פתוח, מחקרי. מפענח פרוטוקולים לא מוכרים | כלי למומחים, לא מוצר שמייצר תאום מוכן לשימוש |
| **AALpy / LearnLib** | ספריות ללמידת מכונות מצבים | רק ספריות. אין הקלטה, תאום או דוח |

### אז מה אנחנו מוסיפים?

- **הכלים המסחריים** טובים בהרצה, אבל **לא לומדים לבד**.
- **הכלים המחקריים** טובים בלמידה, אבל **לא בונים מוצר**.
- **הרעיון שלנו** הוא לחבר את שלושת הדברים: **לומד לבד, בונה תאום שעובד, ומודד כמה הוא מדויק**, כולל "מפת פערים" שאומרת בכנות מה עוד לא ידוע.

> זה כיוון לבידול, לא הוכחה. צריך לבדוק לעומק כל מתחרה לפני שטוענים שאנחנו ייחודיים. הרשימה מבוססת על ידע כללי ולא על מחקר שוק עדכני.
