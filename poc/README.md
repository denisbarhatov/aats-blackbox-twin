# BlackBox Twin — POC

**מה ה-POC מוכיח:** מערכת יכולה לגלות לבד את המצבים של מכשיר, רק מתוך פקודות ותשובות ובלי לראות את הקוד שלו, ולבנות תאום שמתנהג כמוהו גם על רצפים שלא ראתה.

**תוצאה (הרצה עם ברירות המחדל):**

| | |
|---|---|
| מצבים שהתגלו | 4 מתוך 4 |
| ניסויים מול המכשיר | 203 (פחות משנייה מקומית) |
| התאום צדק ברצפים חדשים | **100%** (300 רצפים) |
| Record & Replay צדק | **27.3%** |
| מעברים שנבדקו | 16 מתוך 16 |

## איך מריצים

צריך רק Python 3.10 ומעלה, בלי התקנות.

```bash
cd poc
python run_demo.py
```

בהצגה חיה, עם עצירה בין השלבים:

```bash
python run_demo.py --pause
```

בסוף נוצר הדוח `out/report.html`. פותחים אותו בדפדפן. התרשים נטען מהאינטרנט, והטבלאות מוצגות גם בלי חיבור.

בדיקה אוטומטית:

```bash
python -m unittest test_poc
```

## מה יש פה

| קובץ | תפקיד |
|---|---|
| `device_sim.py` | **הקופסה השחורה**: סימולטור של ESP32 עם נורה. רץ כתהליך נפרד, ומדברים איתו רק דרך TCP |
| `learner.py` | **מנוע הלמידה**: אלגוריתם L\* שכתבנו בעצמנו. שולח ניסויים ובונה מכונת מצבים |
| `model.py` | המודל שנלמד, ופורמט `model.json` |
| `twin.py` | **התאום**: שרת שטוען את `model.json` ועונה לפיו. תומך גם בהזרקת תקלות (`--fault-rate`) |
| `baseline.py` | Record & Replay: ההשוואה שצריך לנצח |
| `validator.py` | בדיקה דיפרנציאלית: אותם רצפים חדשים למכשיר ולמועמד |
| `led_app.py` | "אפליקציית המפעל": מדברת עם המכשיר או עם התאום, לפי הפורט |
| `report.py` | בונה את הדוח |
| `run_demo.py` | מריץ הכל לפי הסדר |

## המכשיר הנסתר

הלומד **לא** רואה את הטבלה הזאת. היא נמצאת רק ב-`device_sim.py`, ומשמשת לבדוק שהלמידה הצליחה.

| מצב | `ON` | `OFF` | `STATUS` | `PING` |
|---|---|---|---|---|
| `OFF` | `OK` → ON | `OK` | `LED_OFF` | `PONG` |
| `ON` | `WARN` → WARN | `OK` → OFF | `LED_ON` | `PONG` |
| `WARN` | `ERR` → FAULT | `OK` → OFF | `LED_ON` | `PONG` |
| `FAULT` | `ERR` | `ERR` | `FAULT` | `ERR` |

`RESET` מחזיר תמיד ל-`OFF` ועונה `RESET_OK`.

**החלק המעניין:** `ON` ו-`WARN` עונים אותו דבר ל-`STATUS` (`LED_ON`). אי אפשר להבדיל ביניהם מבחוץ בשאלה אחת, ובכל זאת המערכת גילתה שהם שני מצבים שונים.

## איך הלמידה עובדת (L\*)

1. הלומד יודע רק כתובת, רשימת פקודות מותרות ופקודת איפוס.
2. **ניסוי** = איפוס, רצף פקודות, רישום התשובות.
3. הלומד ממלא טבלה: שורה לכל רצף שמגיע למצב כלשהו, ועמודה לכל רצף בדיקה. **שתי שורות עם תשובות שונות הן שני מצבים שונים.**
4. כשהטבלה סגורה (כל צעד מוביל למצב מוכר), נבנית **השערה**.
5. ההשערה נבדקת מול המכשיר ב-200 רצפים אקראיים. אם נמצא הבדל, הוא הופך לעמודה חדשה והלמידה ממשיכה. אם לא, המודל נשמר.

## תסריט להצגה (בערך 5 דקות)

1. **הבעיה (30 שניות):** "יש מכשיר בלי קוד מקור ובלי תיעוד. רוצים לבדוק תוכנה מולו בלי לגעת בו."
2. **הקופסה השחורה:** להריץ `python run_demo.py --pause`. בשלב 1 להסביר שהמכשיר רץ כתהליך נפרד, ושהלומד יודע רק כתובת ורשימת פקודות.
3. **הלמידה:** בשלב 2 רואים את המצבים מתגלים אחד אחרי השני: `[ON]`, `[ON ON]`, `[ON ON ON]`.
4. **ההוכחה:** בשלב 4: 300 רצפים שהמערכת לא ראתה. התאום 100%, Record & Replay 27%. להראות את הדוגמה `ON ON STATUS`, שבה Record & Replay טועה.
5. **ההחלפה:** בשלב 5, אותה אפליקציה מול המכשיר ומול התאום, ואותן תשובות.
6. **הדוח:** לפתוח את `out/report.html` ולהראות את גרף המצבים.
7. **הצעד הבא:** ESP32 אמיתי ו-AWS IoT Core (`docs/POC_PLAN.md`).

שאלות שכדאי להתכונן אליהן:
- **"אולי פשוט הקלטתם את התשובות?"** — Record & Replay מקבל אותה כמות נתונים ומגיע ל-27%. וגם: הבדיקה נעשית רק על רצפים שהלומד לא שלח.
- **"איך אתם יודעים שהמודל נכון?"** — לא מוכיחים שהוא מושלם. מראים שלא נמצא הבדל ב-300 רצפים חדשים, וגם הבדיקה האקראית של L\* לא מצאה. וזה כתוב בדוח בסעיף "גבולות".
- **"איפה AWS?"** — ה-POC מוכיח את הליבה. השלב הבא: IoT Core לחיבור ה-ESP32, Fargate ללומד ולתאום, S3 למודל, ו-Step Functions לתזמור.

## גבולות

- מכשיר מדומה, ופרוטוקול טקסט פשוט מעל TCP.
- המכשיר צריך פקודת איפוס.
- מצבים פנימיים שלא משפיעים על התשובות לא ניתנים לגילוי מבחוץ.
- בדיקה אקראית לא מוכיחה נכונות מלאה.
